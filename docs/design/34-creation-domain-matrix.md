# 34 创作域能力矩阵（通用件定位）

## 背景与问题

产品定位是通用创作工具：小说、剧本、分镜、非虚构、诗歌、游戏叙事、文案等都在目标域内，不做单类型专精。当前能力分布不均——小说域已达 S 档，多个创作域只有骨架或完全缺位，且没有一份把"每个创作域要到什么程度"说清的基线，导致排期靠感觉。

## 目标

- 定义统一档位：**A 档 = 该创作类型可以用本工具从零写到成稿，结构/编辑/AI 辅助/导出/数据安全五个环节都不缺；S 档 = 在 A 之上具备该类型独有且领先的能力**。
- 逐域标注现状与目标，把每个"缺"指向对应设计稿，形成可排期的总表。
- 明确"通用件"的取舍：不为单类型堆专有交互，A 档能力尽量用通用数据模型（实体类型/字段/视图/顺序）承载，专有部分靠类型模板与发行档。

## 非目标

- 不为任何单类型做超出 A 档的专有编辑器（如在画布内直出漫画分镜图），这类能力留给插件生态。
- 不做平台侧能力（发布、社区、收益、平台合规预审）。

## 设计

### 档位定义

- **缺**：该环节无实现。
- **A**：可用通用能力完成，环节无硬缺。
- **S**：有该类型独有且明显领先的能力。

## 验收

- 每个创作域在"结构/编辑/AI/导出/安全"五环节都有可运行路径，且用一份示例工程走通到导出。
- 新创作类型只用"类型模板 + 字段 + 视图"落地，不改核心；核心数据模型不因引入类型出现专用表或专用字段。
- 本表每季度复核一次，落到 `docs/features/`。

## 风险

- 域太多导致核心腐化：以"通用数据模型承载 + 模板扩展"为唯一扩展方式，出现专用分支即判违规。
- A 档标准被泛化稀释：验收要求每个域有一份真实示例工程走通全链路。
